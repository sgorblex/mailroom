# Glossary

| Term | Meaning |
| --- | --- |
| **User** | A person who signs in to Mailroom. Their accounts, filters and suggestions are theirs alone. |
| **Admin** | A user who may also add and remove users and reset their passwords. The first user is one, made with `mise run create-user <name> --admin`. |
| **User session** | One browser signed in as a user: a random token in the `mailroom_session` cookie, valid until it expires or the user signs out there. |
| **Account** | One mailbox a user reaches over IMAP (read) and SMTP (send), with its identities and send mode. Modelled by mailroom-core. Named by the user (its name, unique among their accounts, and colour; the web shows its login when it has no name), and by its **account id** for the API and MCP: a positive integer the instance gives it and never reuses, never shown in the web. One a rule set or an audit record still names after it is gone is a *Removed account*, never its id. |
| **Sender authentication** | Whether a message's sender passed SPF, DKIM and DMARC, as the account's **authentication server** recorded it: the account's optional `authserv_id` (`mx.google.com` for Gmail), set by the user or a provider's preset. Only the topmost Authentication-Results field carrying that id is believed (RFC 8601); any other may be forged. Without one, no result is believed and a sender is *not verified*. Never chosen by the IMAP host. [`requirements/mail-client.md`](requirements/mail-client.md) — *Account autoconfiguration*, and the read's `authentication`. |
| **Sender mismatch** | A From display name holding an address or domain other than the real one (`service@paypal.com <x@evil.example>`): a read warns, never quoting the name. A dotted word is a domain only when it ends in a real top-level domain ("Node.js" is none); a domain counts as the real one's only as its parent or child, so "Amazon.co.uk" from amazon.com warns. [`requirements/mail-client.md`](requirements/mail-client.md) — the read's `sender_mismatch`. |
| **Sent to** | The account's identity a message arrived at: its To, then Cc, then delivery addresses, the first that is one. The identity a reply or forward is sent from by default. |
| **Audit record** | What one write did, or tried to do, to one message: who acted (the user, an agent and its app, or a filter), the action, the result and the message's identifying fields, never its subject or body. [`requirements/nonfunctional-requirements.md`](requirements/nonfunctional-requirements.md) — *Audit trail*. |
| **Identity** | A `From` address an account may send as. |
| **Signature** | The text an **identity** signs its messages with, written by the user on their *Profile* page in the composer's rich editor and kept as sanitised HTML with its text. A message from the identity starts with it in a marked block (`data-mailroom-signature` in HTML, below `-- ` in text), below where the user writes and above a quote; changing `From` swaps it while untouched. An agent's draft or send gets it too, unless it asks not to. [`requirements/mail-client.md`](requirements/mail-client.md#signatures). |
| **Send mode** | Per account: `off`, `drafts`, `approval`, `direct` — what an **agent** may do when it sends (mailroom-core's send gate): `off` refuses it and the draft tools, `drafts` saves a draft instead, `approval` sends only if every recipient is auto-approved and otherwise saves the whole message as a draft, `direct` sends. The user's own *Send* in the web client overrides it, except `off`. [`requirements/mail-client.md`](requirements/mail-client.md). |
| **Send gate** | mailroom-core's single path to SMTP: it checks the send mode (and who is acting, user or agent), the recipients and the limits, counts the send before it is made, and hands out the only token that `deliver` accepts. [`requirements/mail-client.md`](requirements/mail-client.md). |
| **Held send** | A draft held for the worker to send at a set time, through the **send gate** as whoever scheduled it: one mechanism for undo send and send later. Until the worker takes it, cancelling it leaves the draft in Drafts and nothing sent. The web's Send holds a message for the user's Undo delay (`undo_send_seconds`, 0 to 30 s, 10 by default; 0 sends at once), and Undo cancels it and opens the draft again; *Send later* holds it until a time the user picks, and the *Scheduled* list cancels or edits it. [`requirements/mail-client.md`](requirements/mail-client.md#undo-send) — *Send state machine*. |
| **Draft** | A message in the account's `\Drafts` folder. The web client always composes through one; saving makes a new version and then removes the old one. [`requirements/mail-client.md`](requirements/mail-client.md). |
| **Index** | The app's local copy of each indexed folder's message metadata (addresses, subject, dates, flags, size, thread headers, the snippet; never a body), for lists, counts and search without a round of IMAP per query; refs still name the message on the server, where every action runs. [`requirements/nonfunctional-requirements.md`](requirements/nonfunctional-requirements.md) — *Mail metadata at rest*. |
| **View** | A list of the user's mail kept in the sidebar, read from the **index** only: *All inboxes* (INBOX of every account), built in, or a saved view, some folders of any of the user's accounts or a search in the search syntax. Not the **message view**. [`requirements/mail-client.md`](requirements/mail-client.md#views). |
| **Live update** | A change on the server (new mail, a flag or move from another client) reaching the open web app without a reload, via the worker's IMAP IDLE. |
| **Ref** | An opaque string naming one message exactly (account, folder, UIDVALIDITY, UID), as in mailroom-mcp; stale once the folder's UIDVALIDITY changes. [`requirements/mail-client.md`](requirements/mail-client.md). |
| **Remote content** | Images a message loads from the internet (tracking pixels among them): blocked, and revealed per message on request, or at once for a sender the user remembered, only where DMARC passed for the message's one From (**Sender authentication**; [`requirements/mail-client.md`](requirements/mail-client.md) — *Remote content*). |
| **Mailing list** | Mail a list sends, which says so in its List-* fields (RFC 2369, 2919): its List-Id, and links to its archive, to post, for help and to unsubscribe, `https:` or `mailto:` only. Written by the sender, so believed only as far as **Sender authentication** goes. [`requirements/mail-client.md`](requirements/mail-client.md) — the read's `headers.mailing_list`. |
| **One-click unsubscribe** | Leaving a **mailing list** by RFC 8058: the app POSTs `List-Unsubscribe=One-Click` to the list's `https:` link, when the user asks on one message and only where a DKIM signature the account's authentication server passed signs both List-Unsubscribe fields. The one request Mailroom makes to a host a message names. A list offering only a `mailto:` link gets a draft the user sends instead. [`requirements/mail-client.md`](requirements/mail-client.md) — *One-click unsubscribe*. |
| **Archive** | The account's folder with role `archive`; archiving moves messages there. [`requirements/mail-client.md`](requirements/mail-client.md). |
| **Folder** | A mailbox of an account, named by its path: segments joined by the account's hierarchy delimiter (`Archive/2026`); a rule set stores the segments. INBOX and the folders with a role (Sent, Drafts, Trash, Junk, Archive…) are the account's own; the user creates, renames and deletes the others ([`requirements/mail-client.md`](requirements/mail-client.md#folder-management)). A `\Noselect` folder only holds others. |
| **Trash** | Moving messages to the account's folder with role `trash`. Never a permanent delete: trashing does not delete or expunge mail. Mailroom deletes only deliberately: a filter's `delete`, a folder's delete, and the expunge of a draft Mailroom wrote ([`requirements/mail-client.md`](requirements/mail-client.md#the-own-draft-exception)). |
| **Message view** | A message as the client shows it: headers, the text body, attachments, and the HTML view when the message has an HTML body. |
| **Rule set** | An ordered list of filters for one account folder, with one trigger and a **marker**: the mark it is limited to (none, the star or To sort), cleared once a message is handled. A **rule set for all accounts** (`account_id` `all`) runs on INBOX of each account whose Run filters is on, a run per account. [`requirements/filters.md`](requirements/filters.md). |
| **Muted thread** | A conversation the user muted on one account: its new messages in INBOX arrive marked read, nothing moved, by the account's hidden mute **rule set**, so only while its Run filters is on. Known by Message-IDs (the muted message's, those it cites, and each matched since) and on Gmail by its thread, never by subject. [`requirements/filters.md`](requirements/filters.md#muted-threads). |
| **Transfer ledger** | The app's list of the copies a filter's move to another account made (account, folder, UIDVALIDITY, UID), which every run of that folder leaves alone: the guard against moving them on or back. [`requirements/filters.md`](requirements/filters.md#moves-to-another-account). |
| **Filter** | A rule (criteria plus actions) that sorts mail on the server, stored as its spec and run by the filter engine in the app's worker. |
| **Filter engine** | `mailroom_core.filters`: criteria, actions, rules as data (specs), the runner and the IDLE monitor. It was imap-thingy, a library of its own on PyPI, until 2026-11-11; [`core.md`](core.md) — *Filters*. Not the app's `mailroom.filters`, the feature built on it. |
| **To sort** | A mark on a message, the IMAP keyword `$MailroomSort`, for mail waiting to be sorted. Only a server that keeps keywords (PERMANENTFLAGS holding `\*`) can store it, and a Gmail account counts as one that cannot. [`core.md`](core.md) — *Organize*. |
| **Trigger** | What starts a rule set's run: `new_mail` (IMAP IDLE), `scheduled` (every so many minutes) or `manual` (only *Run now*). |
| **Run filters** | The per-account switch, off by default, without which the worker runs no rule set of that account. |
| **Dry run** | Evaluating a rule set against real mail and reporting what each filter would match and do, changing nothing. |
| **Suggestion** | A filter proposed from a user's own triage, with its evidence; inert until that user accepts it. |
| **Profile** | A user's own page for their password, linked sign-ins, signatures and connected apps. (In mailroom-mcp, a connector scope `/mcp/<profile>`; the app has none: its tool groups are instance config and each connected app's approval.) |
| **Tool group** | A named set of MCP tools (`filters_read`, `filters_write`, `filters_run`, `mail_read`, `mail_organize`, `mail_transfer`, `mail_folders`, `mail_draft`, `mail_send`, `audit_read`) with a status (`stable`, `preview`, `planned`); `MAILROOM_MCP_TOOL_GROUPS` picks which are served, and each connected app's grant which of those it may use. A tool several groups need (`accounts_list`, `folders_list`) is served when any of them is. [`requirements/mcp.md`](requirements/mcp.md). |
| **Connected app** | An MCP client a user approved through the built-in OAuth server (an OAuth grant), for the tool groups they chose; listed on their profile, where they change its groups or revoke it. |
| **DCR** | Dynamic client registration (RFC 7591): an MCP client registering itself at `/oauth/register`, limited to the redirect allowlist. [`requirements/mcp.md`](requirements/mcp.md). |
| **CIMD** | Client ID metadata document: an MCP client whose `client_id` is an https URL on an allowed host, serving its own metadata, which the built-in OAuth server fetches and caches instead of a registration. |
| **Authorization request** | An MCP client's `/oauth/authorize` call, stored until a signed-in user approves or denies it on `/connect`; the first user to open it claims it (in `oidc` mode, the SSO sign-in for it). |
| **Linked sign-in** | An identity at the SSO provider (issuer and subject) tied to one user, so they can sign in through SSO (to connect an MCP client too, in `oidc` mode) and, in external mode, use that provider's MCP tokens. |
| **Feature** | One of the optional parts an instance runs on top of the base (users, sign-in, accounts, the settings screens): `mail` (the mail client), `mcp` (the MCP server) and `filters`. `MAILROOM_FEATURES` lists them. [`REQUIREMENTS.md`](REQUIREMENTS.md) — *Editions*. |
| **Edition** | The set of features one instance runs, from the base alone to all three. |
| **Worker** | The app's background process: IDLE, indexing, filter runs, learning. |
